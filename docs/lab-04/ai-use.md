## My Reflection

Iterating on the engineering contract with two complementary AI tools—Gemini for rapid architecture drafting and Codex for rigorous independent critique—exposed several critical subtleties before writing a single line of application code.

The three rounds of independent review highlighted that "almost right" specifications can cause severe implementation bugs down the road:
1. **Durable Idempotency:** Simply checking a key at the start of a controller is insufficient. If the check occurs after a gate (such as checking if the ticket is open), a lost response during network retries would fail if the ticket resolved in the interim. By normalizing the payload into a canonical SHA-256 fingerprint and evaluating the idempotency key *before* mutable gates, we guarantee safe, identical replays under all network conditions.
2. **Dashboard Drill-Down Precision & Entity Scoping:** In real applications, clicking an "Unassigned" card that navigates to a queue including cancelled tickets produces immediate confusion. Furthermore, a card counting 5 Pending Actions might only span 3 Tickets. Designing explicit query contracts like `statusGroup=active` and labeling drill-downs as "View tickets containing these actions" cleanly separates Action counts from Ticket records.
3. **Decoupled Attribution vs. Nominal Assignment:** In team ticketing systems, an action assigned to Alice may frequently be completed by Bob when Alice is off shift. Assuming `completedBy == assignee` corrupts audit attribution and operational metrics. Modeling `completedById` as an explicit field populated upon completion by the authenticated actor accurately reflects team workflows.
4. **Active vs. Passive Invariants:** Relying solely on foreign key cascade restrictions does not prevent someone from executing a raw SQL `DELETE FROM "ActionTakenHistory"`. Adding a database trigger makes the append-only promise truly verifiable and enforceable.
5. **Realistic Recovery Drills:** A database backup rehearsal that re-imports into the live database with altered schema names does not test true disaster recovery. Rehearsing against a completely separate disposable database (`toktickit_recovery_test`) validates that sequences, schemas, and data restore cleanly in a production-like environment.

Treating these reviews as an iterative pre-PR engineering critique helped us establish a watertight contract ready for peer submission and feature implementation.
