## My Reflection

The useful part was checking what happens when a response is lost or only one
attachment fails. Reusing the same submission key lets the server return the
original ticket. A file-storage failure should identify the failed file without
losing the valid ticket. These cases needed tests, not just a working submit button.

AI was most useful when checking how the documents fit together. A requirement can look clear on its own but still conflict with an API response or have no test that proves it. Comparing the specification, API, UI, and test plan helped catch those gaps before coding.

The peer review also showed why failure cases matter. Creating a ticket and uploading a file are separate steps, so the contract needs to explain what happens if only one succeeds. I also learned that a test plan is not evidence of passing tests: results must stay pending until the tests actually run.

When implementing the My Tickets workflow, the key technical challenge was ensuring requester isolation and deterministic pagination. Filtering tickets strictly by `requesterId` at the database query level guarantees that no cross-tenant ticket leakage occurs even if someone guesses query parameters. Adding secondary sorting by `ticketNumber desc` prevented unstable pagination ordering when tickets share identical timestamps or priorities. On the UI side, separating the empty state (no tickets created yet) from the no-search-results state (filters matched nothing) gave users a clear recovery path with a quick 'Clear Filters' button.

For Ticket Detail and attachments, the trickiest part was handling concurrency and tenant isolation. When multiple uploads happen simultaneously, checking the attachment count in application code isn't enough because two requests could read 4 active files at the same time and both insert, pushing the total past 5. Using PostgreSQL transaction-level advisory locks tied to the ticket ID ensured that uploads queue up and enforce the strict 5-file cap reliably. On soft removal, keeping the file on disk while returning `410 Gone` for content requests balanced audit compliance with security, ensuring removed sensitive files can never be viewed or downloaded again.

For E2E verification and release documentation, setting up Playwright to test the whole requester journey against real browser engines gave us a ton of confidence. It caught subtleties like focus management in modals, ensuring `Shift+Tab` and `Tab` wrap properly inside the removal dialog and restore focus back to the triggering button on Escape. Seeing the views render smoothly without horizontal scrolling across Desktop (1440x900), Tablet (834x1112), and Mobile (390x844) proved our CSS and layout decisions held up. Also, realizing that the `P2022` error was just normal schema drift on the local development database—which was easily fixed with `npx prisma migrate deploy` rather than wiping out existing data—reinforced the importance of proper migration discipline over ad-hoc schema resets.
