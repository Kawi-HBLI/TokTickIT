# Lab 2 REST API Contract

## 1. Conventions

### Base URL

```text
http://localhost:8000/api
```

All JSON responses use UTF-8. Date/time values use ISO 8601 UTC strings. Resource IDs are positive integers.

### Development Requester Context

Lab 2 does not implement authentication. Requester-owned Ticket and Attachment endpoints require:

```http
x-requester-id: 1
```

The header is a testing context only and can be changed by the client. It must not be described as secure authentication.

- `GET /api/requesters` does not require a Requester context because it is used before selection.
- Category and Related System reference endpoints do not require ownership context.
- Ticket and Attachment endpoints use `x-requester-id` as the only identity source.
- A `requesterId` in a request body is rejected as an unexpected field rather than accepted as an alternative identity source.
- Missing, malformed, unknown, or inactive context returns `400 Bad Request`.
- A missing resource and a resource owned by another Requester both return the same `404 Not Found` response.

### Idempotent Ticket Creation

`POST /api/tickets` requires a UUID generated by the frontend for one logical submission:

```http
Idempotency-Key: 6aa9ca67-a155-4a67-96f0-e2e6f977c89d
```

- First successful use returns `201 Created`.
- Retrying the same key with the same normalized Ticket payload returns the original Ticket with `200 OK`, header `Idempotency-Replayed: true`, and creates no duplicate.
- Normalization trims text and parses IDs; attachment order, safe original name, MIME, size, and a content digest are included in the comparison. A replay returns the saved original creation response, including any attachment warnings, and does not upload the files again. Internal fingerprints/receipts are not public response fields.
- Reusing the key for a different normalized payload returns `409 Conflict`.
- A new user-initiated submission uses a new UUID.

### Success Envelopes

Single resources:

```json
{
  "data": {}
}
```

Collections:

```json
{
  "data": []
}
```

Ticket creation may also include non-fatal Attachment warnings:

```json
{
  "data": {},
  "warnings": []
}
```

### Error Envelope

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Some values are invalid.",
    "fields": [
      {
        "field": "summary",
        "message": "Summary must contain 5 to 100 characters."
      }
    ],
    "retryable": false
  }
}
```

- `fields` is included only for field/file/query validation.
- `retryable` tells the UI whether a Retry action is meaningful.
- Responses never expose stack traces, SQL/database details, stored filenames, filesystem paths, or raw exception messages.

### Common Status Codes

| Status | Use |
|---|---|
| `200 OK` | Successful retrieval, successful soft removal, or idempotent replay |
| `201 Created` | First successful Ticket or Attachment creation |
| `400 Bad Request` | Missing/invalid context, fields, IDs, enums, query values, or removal reason |
| `404 Not Found` | Missing or differently owned Ticket/Attachment |
| `409 Conflict` | Idempotency-key payload conflict, repeated removal, or active Attachment limit |
| `410 Gone` | Preview/download requested for a soft-removed Attachment |
| `413 Payload Too Large` | A file exceeds 5 MiB |
| `415 Unsupported Media Type` | File type is not JPG/JPEG, PNG, WEBP, or PDF |
| `500 Internal Server Error` | Safe unexpected backend/storage/database failure |

## 3. Tickets

### 3.1 Create Ticket

```http
POST /api/tickets
x-requester-id: 1
Idempotency-Key: 6aa9ca67-a155-4a67-96f0-e2e6f977c89d
Content-Type: multipart/form-data
```

#### Form Fields

| Field | Type | Required | Rules |
|---|---|---|---|
| `categoryId` | integer | Yes | Active Category ID |
| `relatedSystemId` | integer | Yes | Active Related System ID |
| `summary` | string | Yes | Trimmed, 5-100 characters |
| `description` | string | Yes | Trimmed, 10-2,000 characters |
| `requestedPriority` | enum | Yes | `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |
| `attachments` | files | No | 0-5 JPG/JPEG, PNG, WEBP, or PDF files; maximum 5 MiB each |

`requesterId`, Ticket Number, Ticket Date, current status, IT Priority, Ticket Owner, and timestamps are not accepted as editable fields.

All files are validated before Ticket creation. Unsupported, oversized, or count-invalid selections create no Ticket.

#### Response - `201 Created`

```json
{

    "id": 41,
    "ticketNumber": "TKT-2026-00041",

    "categoryId": 2,

    "itPriority": null,

    "ticketOwner": null,
    "ticketDate": "2026-08-29T10:00:00.000Z",
    "createdAt": "2026-08-29T10:00:00.000Z",
    "updatedAt": "2026-08-29T10:00:00.000Z",
    "requester": {
      "id": 1,

    },

      "id": 2,

        "sizeBytes": 204800,
        "isRemoved": false,
        "createdAt": "2026-08-29T10:00:00.000Z"
      }

```

#### Partial Attachment Storage Warning

An unexpected storage failure after the Ticket row is created does not remove the valid Ticket. Successfully stored Attachments remain. Incomplete files and metadata are cleaned up, and the response remains `201 Created` with safe warnings:

```json
{
  "data": {
    "id": 41,
    "ticketNumber": "TKT-2026-00041",
    "currentStatus": "NEW",
    "attachments": []
  },
  "warnings": [
    {
      "code": "ATTACHMENT_STORAGE_FAILED",
      "filename": "battery-diagnostic.png",
      "message": "The ticket was created, but this file could not be stored. Add it again from Ticket Detail."
    }
  ]
}
```

#### Errors

- `400 REQUESTER_CONTEXT_REQUIRED`: missing/malformed Requester header.
- `400 INVALID_REQUESTER_CONTEXT`: unknown/inactive Requester.
- `400 IDEMPOTENCY_KEY_REQUIRED`: missing/malformed UUID key.
- `400 VALIDATION_ERROR`: invalid fields, inactive reference values, or unexpected `requesterId`.
- `409 IDEMPOTENCY_KEY_CONFLICT`: same key used with different normalized payload.
- `413 ATTACHMENT_TOO_LARGE`: at least one file exceeds 5 MiB.
- `415 UNSUPPORTED_ATTACHMENT_TYPE`: at least one file fails the type/extension allowlist.
- `500 TICKET_CREATE_FAILED`: safe unexpected failure before a Ticket is successfully created.

### 3.2 List My Tickets

```http
GET /api/tickets
x-requester-id: 1
```

#### Query Parameters

| Parameter | Type | Default | Rules |
|---|---|---|---|
| `search` | string | empty | Trimmed, case-insensitive partial Ticket Number/Summary match |
| `categoryId` | integer | none | Active Category ID |
| `requestedPriority` | enum | none | `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |
| `sortBy` | enum | `updatedAt` | `createdAt`, `updatedAt`, `requestedPriority` |
| `sortOrder` | enum | `desc` | `asc`, `desc` |
| `page` | integer | `1` | One-based, minimum 1 |
| `pageSize` | integer | `10` | Exactly 10, 20, or 50 |

Default secondary ordering is `ticketNumber desc`. Requested Priority descending order is Critical, High, Medium, Low.

Changing search, filters, sorting, or page size is a frontend behavior that sends `page=1`.

#### Response - `200 OK`

```json
{
  "data": [
    {
      "id": 41,
      "ticketNumber": "TKT-2026-00041",
      "summary": "Laptop battery drains quickly",
      "requestedPriority": "HIGH",
      "currentStatus": "NEW",
      "createdAt": "2026-08-29T10:00:00.000Z",
      "updatedAt": "2026-08-29T10:00:00.000Z",
      "category": {
        "id": 2,
        "name": "Hardware"
      },
      "relatedSystem": {
        "id": 7,
        "name": "Corporate Laptop"
      },
      "activeAttachmentCount": 1
    }
  ],
  "pagination": {
    "page": 1,
    "pageSize": 10,
    "totalItems": 1,
    "totalPages": 1,
    "hasPreviousPage": false,
    "hasNextPage": false
  },
  "query": {
    "search": "",
    "categoryId": null,
    "requestedPriority": null,
    "sortBy": "updatedAt",
    "sortOrder": "desc"
  }
}
```

A page beyond the final page returns an empty `data` array with accurate metadata. No owned Tickets and no search/filter matches both return `200`; the frontend distinguishes them using active query values and `totalItems`.

#### Errors

- `400 REQUESTER_CONTEXT_REQUIRED` or `INVALID_REQUESTER_CONTEXT`.
- `400 INVALID_QUERY`: invalid/unknown query parameter, sort value, page, or page size.
- `500 TICKET_LIST_FAILED`: safe retryable unexpected failure.

```json

  "data": [
    {

      "sizeBytes": 204800,
      "isRemoved": false,
```

### 4.2 Add Attachments to Owned Ticket

```http
POST /api/tickets/:ticketId/attachments
x-requester-id: 1
Content-Type: multipart/form-data
```

Form field `attachments` accepts one or more files, limited by the Ticket's remaining active slots. All files are validated before any new file/metadata is retained. An unexpected failure during this endpoint cleans up the attempted batch and leaves existing Attachments unchanged.

#### Response - `201 Created`

```json
{
  "data": [
    {
      "id": 81,
      "originalName": "error-log.pdf",
      "mimeType": "application/pdf",
      "sizeBytes": 512000,
      "isRemoved": false,
      "createdAt": "2026-08-29T10:30:00.000Z"
    }
  ],
  "activeCount": 2,
  "activeLimit": 5
}
```

#### Errors

- `400` for invalid context, malformed Ticket ID, or no files.
- `404 TICKET_NOT_FOUND` for missing/cross-Requester Ticket.
- `409 ATTACHMENT_LIMIT_REACHED` when the requested batch would exceed five active files.
- `413 ATTACHMENT_TOO_LARGE`.
- `415 UNSUPPORTED_ATTACHMENT_TYPE`.
- `500 ATTACHMENT_UPLOAD_FAILED`: attempted batch cleaned up; existing data unchanged.

### 4.3 Preview Active Attachment

```http
GET /api/attachments/:attachmentId/preview
x-requester-id: 1
```

#### Response - `200 OK`

- Streams the original content with its permitted `Content-Type`.
- Uses `Content-Disposition: inline; filename="<safe-original-name>"`.
- Sends `X-Content-Type-Options: nosniff`.

#### Errors

- `400` for invalid context or malformed Attachment ID.
- `404 ATTACHMENT_NOT_FOUND` for missing/cross-Requester Attachment.
- `410 ATTACHMENT_REMOVED` for soft-removed Attachment.
- `500 ATTACHMENT_CONTENT_UNAVAILABLE` for safe retryable storage failure.

### 4.4 Download Active Attachment

```http
GET /api/attachments/:attachmentId/download
x-requester-id: 1
```

Successful response uses the same safe type/name rules as preview with:

```http
Content-Disposition: attachment; filename="<safe-original-name>"
```

Errors match the preview endpoint.

### 4.5 Soft-Remove Owned Attachment

```http
DELETE /api/attachments/:attachmentId
x-requester-id: 1
Content-Type: application/json
```

#### Body

```json
{
  "reason": "Uploaded the wrong diagnostic report"
}
```

`reason` is required, trimmed, and must contain 5-200 characters.

#### Response - `200 OK`

```json
{
  "data": {
    "id": 80,
    "originalName": "battery-diagnostic.png",
    "mimeType": "image/png",
    "sizeBytes": 204800,
    "isRemoved": true,
    "createdAt": "2026-08-29T10:00:00.000Z",
    "removedAt": "2026-08-29T11:00:00.000Z",
    "removalReason": "Uploaded the wrong diagnostic report"
  }
}
```

The original binary remains in local storage for Lab 2 audit retention but cannot be served by preview/download routes. The response does not expose `removedByRequesterId`, stored name, or path.

#### Errors

- `400 VALIDATION_ERROR` for invalid context/ID or missing/out-of-range reason.
- `404 ATTACHMENT_NOT_FOUND` for missing/cross-Requester Attachment.
- `409 ATTACHMENT_ALREADY_REMOVED`; original removal metadata remains unchanged.
- `500 ATTACHMENT_REMOVE_FAILED`; original active state remains unchanged.

## 5. Validation and Storage Rules

### Text and Reference Values

- Strings are trimmed before validation and storage.
- Unknown request-body fields are rejected.
- Category and Related System IDs must reference active records.
- Requested Priority accepts uppercase enum values only.
- Ticket Number, Ticket Date, Requester, status, IT Priority, Ticket Owner, and timestamps are server-controlled.

### Attachment Validation

- Allowed normalized extensions: `.jpg`, `.jpeg`, `.png`, `.webp`, `.pdf`.
- Allowed MIME types: `image/jpeg`, `image/png`, `image/webp`, `application/pdf`.
- Extension and MIME type must agree with the allowlist.
- Maximum size: 5,242,880 bytes per file.
- Maximum active Attachments: five per Ticket.
- Original display name has path components and control characters removed.
- Stored filename is generated using a UUID and is never returned to the client.

### File and Database Consistency

- Incoming files are processed in temporary storage until validation succeeds.
- Invalid creation requests clean temporary files and create no Ticket.
- Unexpected post-creation Attachment storage failures preserve the Ticket and successful files, remove incomplete file/metadata records, and return safe warnings.
- Existing-Ticket upload batches are all-or-nothing for the attempted batch; failed batches clean temporary/permanent attempted files and metadata.
- Soft removal updates audit metadata but retains the physical file. Content routes always verify ownership and `isRemoved = false` before streaming.

## 6. Ownership Query Requirements

Ownership is enforced in the backend database query, not by loading a resource and relying on frontend visibility.

Conceptual examples:

```text
Ticket lookup:
where id = :ticketId AND requesterId = :currentRequesterId

Attachment lookup:
where id = :attachmentId
  AND ticket.requesterId = :currentRequesterId
```

Missing and cross-Requester results use the same `404` code/message. Server logs may retain internal diagnostic context, but client responses do not reveal ownership or existence.
